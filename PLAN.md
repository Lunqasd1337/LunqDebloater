# План разработки LunqDebloater

Дата: 7 ноября 2026 года. Статус: проектирование; реализация ещё не начата.

Этот документ описывает техническое решение. [ROADMAP.md](ROADMAP.md) задаёт этапы и критерии готовности, [AGENTS.md](AGENTS.md) — правила работы с будущим репозиторием. Все три файла предназначены для размещения рядом в корне репозитория продукта. PLAN.md и ROADMAP.md ведутся на русском, AGENTS.md — на английском. Общение с пользователем — на русском, если он явно не попросил другой язык.

## 1. Цель и исходные решения

Создать LunqDebloater — настольную программу для подготовки установочных образов Windows 11 23H2 и новее: редактирование приложений, Optional Features и Capabilities, интеграция обновлений, драйверов, встроенных твиков и пользовательских REG-файлов, сборка загрузочного ISO. Программа должна самостоятельно скачивать подходящие обновления и предлагать драйверы по оборудованию текущего ПК либо выбранной модели платы.

Принятые рабочие решения:

- Название: LunqDebloater. Публичный репозиторий: https://github.com/Lunqasd1337/LunqDebloater. Выбранная лицензия кода проекта: MIT; наличие LICENSE в репозитории ещё требуется проверить. Лицензия проекта не распространяется автоматически на пакеты Microsoft и производителей.
- Приоритетные производители плат: ASRock, GIGABYTE, MSI, ASUS. Начать с одного адаптера для проверки архитектуры, затем реализовать остальные; конкретный порядок и пилотные модели определить в R0.
- Обязательные провайдеры видеодрайверов: AMD и NVIDIA. Предусмотреть определение всех GPU текущего ПК, ручной ввод с выбором точной модели и импорт профиля оборудования; после поиска программа предлагает скачать и интегрировать подходящие драйверы в целевой образ.
- Пользователь может предоставить ISO Windows 11 23H2, 24H2, 25H2 и 26H2. Он сам подготовит окружение R0, проверит версии инструментов, метаданные и хеши ISO, совместимость источников FoD и конфигурацию Hyper-V.
- Пилотное оборудование пользователя: ASRock B650 PG Lightning WiFi, NVIDIA GeForce RTX 5060 8 GB (не Ti), AMD Ryzen 7 7800X3D. Ревизию платы и фактические Hardware IDs получить при инвентаризации; наличие оборудования не означает разрешение переустанавливать рабочую ОС. Доступность встроенной графики AMD проверить по фактическому профилю устройств; дискретная AMD-карта пока не заявлена.
- Интерфейс: русский и английский языки, переключение и сохранение выбора; светлая, тёмная и системная темы. Системный режим следует теме Windows и реагирует на её изменение. Все пользовательские строки хранить в ресурсах локализации; язык приложения не меняет язык общения агента с пользователем.
- В первой версии интегрируются видеодрайверы. NVIDIA App, AMD Software и другие дополнительные приложения — отдельная последующая функция, согласованная пользователем.
- Получено пять пользовательских REG-файлов: телеметрия, пара настроек предлагаемых приложений и пара политик драйверов Windows Update. Неизменённые копии находятся в `docs/registry/examples/`, описание и ограничения — в [документации REG-примеров](docs/registry/README.md), SHA-256 — в `docs/registry/manifest.json`. Содержимое прочитано, явных секретов и персональных данных не обнаружено. Применение к реестру и испытания в VM не выполнялись. Упомянутый внутри пресета файл Restore Windows Telemetry.reg не предоставлен. Для следующих файлов сохраняется проверка перед публичным Git; чувствительные оригиналы хранить вне репозитория.
- C#, .NET 10 LTS, WPF, MVVM. Конкретные версии SDK и зависимостей фиксируются после проверки поддержки хостовых ОС.
- UI работает без повышения прав; операции обслуживания выполняет отдельный процесс с повышенными правами.
- DISM — основной механизм обслуживания. Сначала адаптер CLI для вертикального прототипа, затем DISM API там, где это даёт структурированные результаты и надёжный прогресс.
- SQLite — локальные задания, журнал и индекс кэша; JSON — переносимые проекты и подписанные каталоги.
- GitHub Releases и Velopack — базовый вариант обновления приложения.
- В первой версии — хост Windows 11, приложение и целевые образы только x64 (подтверждено пользователем; не 32-битная x86). ARM64 и Windows 10 не входят в текущий объём. Целевые выпуски для первой матрицы: Windows 11 23H2, 24H2, 25H2, 26H2; один выбранный индекс WIM за сборку.
- Цель — поддержка всех редакций Windows 11, а не ограничение Home/Pro. Список редакций получать из образа, доступность операций определять по конкретной edition/build. Home, Pro, Enterprise, Education и специальные варианты включать в проверяемую матрицу по мере получения соответствующих образов. LTSC/IoT/N и другие варианты не считать проверенными автоматически по факту поддержки обычной редакции. Поддержка разных редакций не означает одновременное обслуживание всех индексов.
- Пользователь подтвердил: «Compability» означает Capabilities / Features on Demand.
- Программа не изменяет установленную Windows: разрешённые обращения к хосту ограничены определением оборудования, проверкой окружения и обслуживанием рабочих образов.

Диапазон Windows 11 23H2+ обозначает цель поддержки, а не гарантию совместимости с любой будущей сборкой. Конкретные редакции, сборки, языки и ревизии плат фиксируются в матрице после проверки. Возможность редактировать образ и наличие доступных для его редакции обновлений оцениваются отдельно.

## 2. Границы первой публичной версии

Включить:

1. Импорт ISO/WIM/ESD, выбор редакции, инвентаризацию и экспорт нового WIM/ISO.
2. Управление provisioned AppX, Features и Capabilities с проверкой источников.
3. Интеграцию локальных INF-пакетов, CAB/MSU и REG-файлов.
4. Каталог встроенных твиков с применимостью, конфликтами и предпросмотром.
5. Автоматическое скачивание обновлений для явно перечисленных веток Windows.
6. Определение оборудования, ручной выбор модели платы или GPU, импорт профиля оборудования, один работающий провайдер драйверов плат и оба провайдера видеодрайверов AMD/NVIDIA для явно проверенного набора моделей.
7. Сохранение проекта, повторную сборку, отчёт, диагностику и восстановление после сбоя.
8. Обновление самой программы из GitHub.

Не включать в первую версию: произвольное удаление защищённых CBS-компонентов; массовое удаление WinSxS; универсальную установку Win32-приложений офлайн; обход лицензирования; прошивку BIOS; установку драйверов в текущую Windows; обновление между произвольными ветками Windows; универсальную поддержку всех производителей.

## 3. Пользовательский процесс

1. Создать проект и выбрать исходный образ, рабочий каталог и выходной файл.
2. Прочитать редакции и выбрать индекс. Показать архитектуру, сборку, языки и состояние поддержки.
3. Проверить ADK/DISM, файловую систему, права, свободное место и существующие монтирования.
4. Создать рабочую копию, смонтировать её и получить инвентаризацию.
5. Настроить вкладки: приложения; Features; Capabilities; обновления; драйверы; твики; REG-импорт.
6. Сформировать предварительный план: операции, зависимости, цели обслуживания, загрузки, конфликты и блокирующие ошибки.
7. После выбора «Применить» скачать и проверить пакеты, зафиксировать окончательный план и выполнить его.
8. Проверить результат, выгрузить ульи, сохранить образ и собрать выходной файл.
9. Показать отчёт: применено, пропущено с причиной, отложено до загрузки, ошибки и ограничения проверки.

Изменение флажков в UI не меняет образ немедленно. Неоднозначный REG-контекст и неподтверждённая совместимость драйвера отображаются явно.

## 4. Архитектура и структура решения

```text
src/
  ImageEditor.Desktop/          WPF, MVVM, представления и навигация
  ImageEditor.Contracts/        DTO и версионируемый IPC-протокол
  ImageEditor.Domain/           модели образа, операций, применимости
  ImageEditor.Application/      сценарии, планировщик, управление заданиями
  ImageEditor.Infrastructure/   SQLite, HTTP, кэш, подписи, журналы
  ImageEditor.Servicing/        адаптеры DISM, реестра и сборки носителя
  ImageEditor.Worker/           привилегированный исполнитель
  ImageEditor.Cli/              воспроизводимые сборки и диагностика
tests/
  Unit/
  Integration/
  VmAcceptance/
catalogs/
  tweaks/
  updates/
  drivers/
schemas/
docs/
  adr/
  compatibility/
  test-reports/
tools/
```

Направление зависимостей: Desktop/CLI → Application → Domain; Infrastructure и Servicing реализуют интерфейсы внутренних слоёв. Domain не зависит от WPF, процессов, реестра или сети. Contracts не содержит UI-типов.

Основные интерфейсы: `IImageService`, `IInventoryService`, `IPlanBuilder`, `IUpdateProvider`, `IDriverProvider`, `IRegistryService`, `IDownloadService`, `IJobStore`, `IMediaBuilder`.

Worker принимает типизированные операции, а не произвольный shell-код. Транспорт — локальный named pipe с ACL, проверкой клиента и сессии, версией протокола и корреляцией сообщений. Worker повторно валидирует аргументы, целевые пути и пакеты независимо от UI. После проверки пакеты помещаются в защищённую область staging либо повторно проверяются непосредственно перед применением, чтобы исключить подмену между проверкой и использованием.

## 5. Модель проекта и планировщик

`ProjectManifest` хранит версию схемы, отпечаток исходного файла, индекс, целевой профиль Windows, желаемые изменения, ссылки на локальные ресурсы и настройки вывода. Переносимые пути задаются относительно проекта, абсолютные пути — только как локальные привязки.

`BuildLock` фиксирует точные версии каталогов, идентификаторы и ревизии пакетов, контрольные суммы, выбранные источники, версию приложения и инструментов обслуживания. Повторная сборка воспроизводит состав и последовательность; побайтовая идентичность ISO не обещается без отдельного режима нормализации временных меток.

Каждая операция содержит: ID, тип, target image/index, параметры, prerequisites, ожидаемое исходное состояние, критерий успешности, возможность повтора, правила отмены и необходимость загрузки Windows для завершения.

Планировщик строит ациклический граф зависимостей. Загрузки независимых файлов можно выполнять параллельно с ограничением числа соединений. Изменения одного образа выполняются последовательно. Перед исполнением проверяются циклы, конфликты и доступность всех источников.

Состояния задания: `Draft → Validating → Ready → Downloading → Servicing → Verifying → Exporting → Completed`. Дополнительные состояния: `Failed`, `CancelRequested`, `Cancelled`, `RecoveryRequired`. Запрос отмены и фактическое завершение отмены — разные события.

## 6. Образы и носитель

- Обслуживать только рабочую копию; исходный ISO/WIM сохранять неизменным.
- Для ESD предусмотреть экспорт в WIM. Split WIM и другие неподдержанные форматы распознавать и объяснять ограничение.
- Не определять индекс редакции по фиксированному числу: читать метаданные образа.
- В первой версии явно предлагать экспорт выбранной редакции в отдельный WIM; не удалять остальные редакции без отражения этого в плане.
- Отдельно моделировать `install.wim`, индексы `boot.wim`, вложенный `winre.wim` и файлы Setup.
- Добавлять boot-critical драйверы в необходимые среды установки и восстановления по отдельным правилам применимости.
- Использовать совместимую установленную версию ADK/DISM, а не произвольную DLL из PATH. Доставку компонентов ADK решать с учётом условий их распространения.
- Создавать ISO через Oscdimg с подходящими загрузочными записями исходного носителя. Экспорт SWM для FAT32 — последующее расширение.
- Публиковать готовый выходной файл только после успешной проверки; частичный файл имеет отдельное временное имя.

## 7. Приложения, Features и Capabilities

Инвентаризация всегда читается из текущего образа. Каталог предоставляет описания и правила, но не подменяет фактическое состояние.

- AppX: перечисление provisioning, удаление и добавление с зависимостями и необходимыми лицензиями. Отдельно определять захваченные образы с существующими профилями; в MVP неподдержанные случаи блокировать с объяснением.
- Features: включение/отключение, проверка родительских функций, источников и состояний pending. Не приравнивать отключение к удалению payload и освобождению места.
- Capabilities: добавление/удаление с совместимым FoD-источником, архитектурой и языковыми зависимостями. Не рассчитывать на автоматическое получение FoD через Windows Update для офлайн-образа.
- CBS: поддерживаемое обслуживание пакетов. Принудительное снятие защиты и ручное удаление системных файлов исключены.
- Проверять, что выбранные изменения не уничтожают источники/зависимости следующих операций.

## 8. Автоматические обновления Windows

Источник истины для подбора — профиль образа и состояние его пакетов. WUA текущего ПК и `wsusscn2.cab` не являются готовым сканером смонтированного WIM.

Поток: каталог → фильтрация применимости → зависимости и supersedence → предварительный план → загрузка → проверка → окончательный план → DISM → повторная инвентаризация.

Запись каталога содержит ID/revision/KB, семейство и ветку Windows, архитектуру, ограничения редакций и языков, класс обновления, prerequisites, supersedes, целевые среды, файлы/размеры/хеши, официальный источник, рецепт применения и дату проверки. Статусы применимости: `Applicable`, `NotApplicable`, `AlreadyPresent`, `Unknown`; `Unknown` не превращается в разрешение установки.

Поддерживать LCU, необходимые SSU, checkpoint-цепочки, обновления .NET Framework; затем Safe OS и Setup Dynamic Update. Preview отключены по умолчанию. Enablement packages разрешать только для явно описанных и проверенных переходов.

Рецепты обслуживания привязаны к ветке Windows: FoD, языки и optional components учитываются до завершающего обновления соответствующих компонентов. Нельзя установить универсальный порядок сортировкой по KB или дате.

Первый провайдер использует подписанный каталог проекта, файлы загружаются с официальных серверов Microsoft. Подготовка каталога: получение метаданных → валидация → испытание на матрице образов → подпись → публикация. Парсер сайта Update Catalog допустим как заменяемый источник кандидатов, но не как единственная гарантия применимости.

Для Windows 11 учитывать конкретную ветку, редакцию и её жизненный цикл. Требование 23H2+ не гарантирует наличие новых обновлений для каждой редакции. Программа не объявляет образ полностью актуальным, если каталог покрывает только часть категорий. Windows 10 не входит в текущий объём.

## 9. Поиск и интеграция драйверов

Три режима: текущее оборудование; ручной выбор модели/ревизии платы или точной модели GPU; импорт профиля с другого ПК. Оборудование компьютера, на котором редактируется образ, не считается целевым без выбора пользователя: образ может готовиться для другого ПК.

Профиль: производитель и модель системы, производитель/Product/Version платы через CIM, Hardware IDs и Compatible IDs через SetupAPI/Configuration Manager. Серийные номера не собирать по умолчанию; не отправлять полный профиль внешним сервисам без необходимости.

Название платы используется для поиска кандидатов. Окончательное сопоставление учитывает Hardware IDs, subsystem, архитектуру и ограничения целевой Windows. Для ноутбуков и OEM-систем предпочтителен каталог модели устройства. Пустые SMBIOS-поля и неизвестная ревизия должны приводить к ручному уточнению, а не догадке.

Провайдер: `SearchModels → GetCandidates → Download → Extract → Inspect`. Начать с одного производителя; отсутствие стабильного каталога фиксировать как стоимость поддержки конкретного адаптера.

Результат поиска показывает источник, версию, дату, размер, поддерживаемую ОС и основание соответствия. Уровни: точное совпадение устройства; пакет для модели; общий пакет чипа; совместимость не подтверждена. Более новая дата не является достаточным основанием выбора.

Интегрировать INF/CAT и payload. EXE/MSI допускаются только как источники извлечения по проверенному рецепту провайдера; не запускать произвольный установщик. Распаковка проверяет выход за каталог, ссылки и лимиты размера. Каталог и входящие файлы проверяются средствами проверки подписей Windows; одной подписи EXE-обёртки недостаточно.

DCH-расширения, Software Components и дополнительные приложения учитывать отдельно. Интеграция в Driver Store не гарантирует выбор пакета PnP или установку панели управления. Экспорт локальных сторонних драйверов — вспомогательная функция, а не замена поиска подходящего пакета для другой Windows.

### 9.1. Видеокарты AMD и NVIDIA

Пользовательский сценарий: «Драйверы → Видеокарты → Определить на этом ПК / Ввести модель / Импортировать профиль → Найти драйверы → Просмотреть кандидатов → Скачать и добавить в план интеграции». Поиск не устанавливает драйвер на хост и не меняет образ до применения плана.

- Автоопределение: перечислить все устройства GPU через SetupAPI/Configuration Manager, получить Hardware IDs, Compatible IDs, PCI VEN/DEV/SUBSYS/REV и отображаемое название. CIM/Win32_VideoController использовать как дополнительный источник названия, а не единственное доказательство модели. Не ограничиваться первым GPU: учитывать встроенную и дискретную графику, гибридные ноутбуки и несколько видеокарт.
- Без установленного видеодрайвера название может быть общим. Использовать доступные аппаратные ID; если точную модель подтвердить нельзя, предложить выбор пользователя. Виртуальный адаптер Hyper-V не выдавать за физическую видеокарту хоста.
- Ручной ввод: производитель AMD/NVIDIA, семейство, точная модель и исполнение Desktop/Notebook; свободный текст приводит к списку совпадений. Нельзя скачивать первый результат по похожему названию. При отсутствии аппаратных ID показывать «кандидат по выбранной модели», а не «точное совпадение устройства».
- Отдельные адаптеры `AmdGraphicsProvider` и `NvidiaGraphicsProvider` реализуют общий `IDriverProvider`. Источники — официальные каталоги/страницы производителей; публичный стабильный API не предполагается без проверки. Получение метаданных и извлечение пакетов оформлять заменяемыми, версионируемыми адаптерами.
- Выбирать пакет для версии, сборки и архитектуры Windows в образе, а не ОС текущего ПК. Проверять поддерживаемые GPU, INF-ограничения, цифровые подписи и зависимости. Для устаревшей модели предлагать последний совместимый пакет либо объяснять отсутствие поддержки, а не выбирать самый новый релиз.
- Показывать версию, дату, размер, источник, поддерживаемую ОС, ветку драйвера, подпись и основание выбора. Для доступных моделей NVIDIA различать Game Ready и Studio; для AMD — категории стабильности/назначения, опубликованные производителем. Не смешивать версии по одному только номеру и не включать предварительные пакеты автоматически.
- Для ноутбуков и OEM-систем учитывать модель компьютера, subsystem и рекомендации OEM, особенно для переключаемой графики. Общий пакет производителя GPU не объявлять эквивалентным сертифицированному пакету конкретного ноутбука.
- Скачивать полный пакет и извлекать необходимые INF/CAT/payload по проверенному рецепту без установки на хост. Проверять граф зависимостей display/extension/software-component пакетов; HDMI/DisplayPort audio показывать отдельным связанным компонентом. Не интегрировать рекурсивно все INF из распакованного установщика без отбора.
- По умолчанию интегрировать видеодрайверы в выбранный install.wim. Не добавлять их автоматически в boot.wim/WinRE: для этого нужны отдельное обоснование, совместимость среды и проверка.
- NVIDIA App, панели управления и AMD Software не считать установленными вследствие добавления INF. Показывать статус дополнительных приложений отдельно; сценарий их установки после развёртывания проектировать и тестировать отдельно.
- Устранить дубли пакетов, если один драйвер обслуживает несколько выбранных GPU. Совпадения и несовместимые ветки разрешать до исполнения. Учитывать конфликт предпочтений с твиком отключения драйверов Windows Update, не меняя его автоматически.

Испытания: ручной подбор и профиль другого ПК, несколько GPU, отсутствие установленного драйвера, неподдержанная модель, legacy-пакет, неподходящая архитектура/сборка, повреждённый архив, OEM-ограничения и повторная сборка из BuildLock. Hyper-V достаточен для проверки подготовки образа и сценариев приложения, но работоспособность физического GPU и ускорения проверяется на реальном оборудовании AMD и NVIDIA.

Официальные материалы подтверждают наличие выбора продуктов и различия OEM-пакетов, но не предоставляют готовую архитектуру обслуживания офлайн-образов: [подбор драйверов AMD](https://www.amd.com/en/resources/support-articles/faqs/GPU-56.html), [AMD Auto-Detect](https://www.amd.com/en/resources/support-articles/faqs/GPU-131.html), [каталог NVIDIA и рекомендации для ноутбуков](https://www.nvidia.com/Download/processFind.aspx?dtcid=1&lang=en-us). Утилита AMD Auto-Detect ориентирована на текущий ПК и не заменяет resolver для целевого образа.

## 10. REG-импорт и встроенные твики

Drag-and-drop добавляет файл в проект, не применяя его к хосту. Парсер создаёт типизированное дерево операций, показывает их пользователю и определяет целевой контекст.

Поддержка: Windows Registry Editor 5.00; явно определённые кодировки; строки и escapes; DWORD/QWORD; бинарные, expandable и multi-string значения; многострочные hex; значения по умолчанию; удаление значений/ключей. Ошибка содержит файл и строку; непонятые операции не пропускаются молча. Старый REGEDIT4 — отдельное решение после проверки кодировок.

Маршрутизация:

| Ветка | Цель |
|---|---|
| HKLM\SOFTWARE | Улей SOFTWARE образа |
| HKLM\SYSTEM | Улей SYSTEM образа |
| HKCU | Явно выбранный шаблон пользователя или применение при входе |
| HKCR | Явный выбор машинной/пользовательской области Classes |
| HKU\SID | Только существующий и явно выбранный профиль |

`CurrentControlSet` разрешается через состояние SYSTEM/Select; неоднозначность блокирует операцию. `HKU\.DEFAULT` не подменяет `Users\Default\NTUSER.DAT`. Учитываются разрядность представления, SID и пути. Не обещать поддержку любой пользовательской настройки через правку Default-профиля.

Рекомендуемый backend — Offreg либо Win32 API с изоляцией временных точек подключения. Сохранять исходные ульи/значения, закрывать все handles до commit. Отложенное применение выполняет ограниченный обработчик декларативных операций в нужном пользовательском контексте; не использовать один системный startup-скрипт для всех HKCU.

Твик содержит ID, описание, источник, диапазон сборок и редакций, контекст, операции, зависимости, конфликты и проверку результата. В первой версии — небольшой проверенный каталог. Отмена до сборки удаляет операцию из плана; восстановление после применения использует исходное состояние, а не противоположное значение.

## 11. Надёжность, кэш и обновление приложения

- Журнал записывается до и после каждой операции; после сбоя выполняется сверка с реальным состоянием, а не слепой повтор последней команды.
- Не обещать транзакционный откат всех DISM-операций. При сомнительном состоянии пересоздавать рабочий образ из исходника и плана.
- Отмена — в безопасной точке или через документированный механизм; не завершать DISM принудительно по обычному тайм-ауту.
- Не очищать чужие mounts и не удалять рекурсивно произвольные пути. Рабочие папки имеют маркер владельца проекта; проверяются нормализованные пути и reparse points.
- Кэш адресуется по хешу. Незавершённые загрузки не считаются валидными; повтор, resume, лимиты и очистка не затрагивают активные задания.
- Контрольная сумма обеспечивает целостность, подпись и доверенный источник — подлинность. Недоступную проверку доверия не отмечать как успешную.
- Updater использует GitHub Releases, stable/beta и SemVer. Не встраивать персональные токены в клиент.
- Приложение и worker обновляются согласованно только после завершения задания и освобождения ресурсов. Новая версия каталога не меняет уже зафиксированный BuildLock.
- Подпись исполняемых файлов и подписанные каталоги; ротация ключей и миграции схем описываются до публичного выпуска.

## 12. Проверка качества

Пользователь самостоятельно проводит проверки образов, испытания в Hyper-V и тесты на физическом оборудовании. Агент описывает шаги и ожидаемый результат, затем фиксирует предоставленные пользователем результаты в матрице совместимости. Статус проверки обновляется после получения результата.

Unit-тесты: REG-парсер и маршрутизация, применимость пакетов, checkpoint-граф, конфликты, миграции схем, SemVer и безопасные пути. Использовать независимые fixtures с заранее известным результатом.

Интеграционные тесты: изолированные рабочие образы, реальные вызовы DISM, отказ загрузки, повреждённые пакеты, неподходящий FoD, занятый mount, отмена и перезапуск. Моки не подтверждают способность Windows установиться.

VM-проверки: загрузка ISO, установка до рабочего стола, создание пользователя, приложения/компоненты/твики, Windows Update после модификаций, WinRE. Secure Boot проверять на подходящей конфигурации VM. Драйверы дополнительно проверять на реальном оборудовании.

Матрица содержит конкретные edition/build/architecture/language, хост, версии DISM/ADK, хеш исходника, план и ссылку на отчёт. Отсутствие проверки помечается `Not tested`. Не выдавать `CheckHealth` за полную проверку целостности; при необходимости использовать поддерживаемый ScanHealth и обязательно функциональные испытания.

Обычный CI выполняет сборку и быстрые тесты. Обслуживание и VM-задания — изолированные Windows runners с подготовленными образами и достаточным диском. Лицензионные ISO не публикуются в репозитории или CI-артефактах.

## 13. Главные риски и решения до начала реализации

| Риск | Действие |
|---|---|
| Нет универсального стабильного каталога драйверов | Ограничить первого провайдера, фиксировать покрытие |
| Изменение правил обновлений Windows | Версионируемые рецепты и обязательные испытания новых цепочек |
| Потеря питания или commit failure | Исходник неизменен, журнал, recovery и пересборка |
| Неоднозначный HKCU/HKCR | Явный контекст, блокировка неоднозначных операций |
| Повреждение будущего Windows Update | Проверка следующего обновления после кастомизации |
| Компрометация поставки пакетов | Подписи, защищённый staging, проверка перед применением |
| Чрезмерная матрица поддержки | Явный ограниченный список проверенных конфигураций |

Открытые решения R0: конкретные edition/build/language в диапазоне Windows 11 23H2+; порядок адаптеров ASRock/GIGABYTE/MSI/ASUS и пилотные модели с ревизиями; схема подписи и хранения ключей; доступные FoD-источники; механизм отложенных пользовательских настроек; ограничения ресурсов и стратегия установки ADK. Название, публичный репозиторий, MIT, хост Windows 11 и значение Capabilities уже подтверждены пользователем.
